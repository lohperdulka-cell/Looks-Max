# FaceMetric

Веб-платформа объективной оценки внешности (ниша looks-max) от **VA digital studio**.

Сервис анализирует пропорции лица по фотографии: извлекает антропометрические
landmark-точки, считает набор метрик (симметрия, canthal tilt, трети лица, jawline,
диморфизм и др.), переводит отклонения от популяционных эталонов в баллы 0–10 и
формирует отчёт с графиками и рекомендациями. Дополнительно: моггбатлы с ELO,
упражнения, ИИ-консультант, прогресс и достижения.

> **Дисклеймер.** Оценка построена на математической модели пропорций лица и
> популяционных ориентирах. Это не медицинское заключение и не объективная истина
> о внешности. Результаты зависят от качества фото, освещения и ракурса.

### MediaPipe основной, InsightFace — резерв

* **MediaPipe FaceMesh (478 точек)** — провайдер по умолчанию: не требует
  скачивания весов (~3.6 МБ `.task`), пик RSS ≈ 237 МБ, то есть влезает в
  бесплатные 512 МБ Render. Пол/возраст не отдаёт, поэтому пол для метрик
  диморфизма берётся из профиля пользователя или из кнопок на странице оценки.
* **InsightFace (buffalo_l)** даёт 106 точек (`2d106det`) с точной разметкой
  контура челюсти и уголков глаз — это лучше для `gonial angle`, `bigonial width`
  и `canthal tilt`. Плюс встроенный `genderage` даёт независимую оценку
  пола/возраста. Минус — 274 МБ RSS даже с обрезкой моделей, поэтому это резерв,
  который включается явно (`ML_PROVIDER_PRIMARY=insightface`).
* Обе модели грузятся **лениво** и кэшируются в памяти процесса (`ML_LAZY_LOAD`).

### Почему async

FastAPI + async SQLAlchemy: запросы к БД, загрузка/обработка изображений и
стриминг ответов LLM не блокируют event loop. Тяжёлые CPU-операции CV выполняются
в пуле воркеров через `run_in_threadpool` (см. API фото на этапе 3), чтобы не
тормозить обработку других запросов.

## Деплой на Render

В репозитории есть `render.yaml` (Blueprint). Render сам создаёт web-сервис и
управляемый PostgreSQL, а `SECRET_KEY` и `JWT_SECRET` генерирует автоматически.

1. Запушьте репозиторий на GitHub.
2. В Render: **New → Blueprint**, выберите репозиторий — Render прочитает `render.yaml`.
3. Дождитесь сборки. Миграции применяются на старте контейнера (`alembic upgrade head`).

Важно про ресурсы: на free-тарифе 512 МБ RAM. Замеры пика RSS (лимит 512 МБ,
жёсткий cgroup):

| Конфигурация | Пик RSS | OOM-kill |
|---|---|---|
| Полный `buffalo_l` (5 моделей) | 920 МБ | да |
| InsightFace, 3 модели | 274 МБ | нет |
| MediaPipe | 237 МБ | нет |
| InsightFace(3) + MediaPipe | 439 МБ | нет |

Поэтому деплой по умолчанию собирается в профиле `mp` (только MediaPipe) и
работает в **реальном режиме**: 478 точек, метрики считаются по фото. Пол для
метрик диморфизма берётся из профиля пользователя или из переключателя прямо на
странице оценки — MediaPipe его не отдаёт, а `genderage` есть только у InsightFace.
Пол влияет на четыре метрики: диморфизм, gonial angle, угловатость челюсти и
canthal tilt. Разница заметная: для одного и того же лица общий балл 4.32 у
мужских эталонов против 4.89 у женских.

Почему полный InsightFace не влезает: `buffalo_l` — это 5 моделей, а коду нужны
три (`det_10g`, `2d106det`, `genderage`). Лишние `1k3d68.onnx` (137 МБ) и
`w600k_r50.onnx` (166 МБ) дают скачок памяти при создании ONNX-сессий. Параметр
`allowed_modules` не помогает: InsightFace создаёт сессию раньше фильтра.
Поэтому модели обрезаются физически — см. `_pruned_buffalo_dir()` в
`app/ml/landmarks.py`.

Профили сборки: `core` — демо-провайдер (синтетическая сетка), `mp` — MediaPipe
и PDF-экспорт (реальные измерения на free, дефолт), `full` — + InsightFace.
Переключить провайдер можно переменными `ML_PROVIDER_PRIMARY`/`ML_PROVIDER_FALLBACK`.

PDF-экспорт включён в `mp`: WeasyPrint добавляет ~45 МБ RSS, замеренный пик
связки MediaPipe + PDF — 321 МБ, то есть запас до 512 МБ есть. В образ добавлены
системные библиотеки pango/cairo/gdk-pixbuf и `fonts-dejavu-core` — без шрифта
с кириллицей текст в PDF вышел бы пустыми квадратами.

## Почта и сброс пароля

Сброс пароля отправляет письмо со ссылкой через SMTP (`app/core/mail.py`).
Отправка включается переменными `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASSWORD`, `MAIL_FROM`. При `SMTP_STARTTLS=false` соединение идёт без
шифрования — это нужно только локальным тестовым серверам.

Если `SMTP_HOST` пуст или сервер недоступен, письмо не уходит, а ссылка
сброса пишется в лог (`auth.reset.email_stub`). Приложение при этом работает:
запрос на сброс отвечает успехом, токен создаётся. Сбой почты не должен
превращаться в отказ сброса пароля, поэтому ошибки SMTP не пробрасываются
наружу. Пароль и токен в лог не попадают — только адрес получателя.

На Render эти переменные заданы в `render.yaml` как `sync: false`, то есть
значения вводятся в панели и не хранятся в репозитории.

## Безопасность мутирующих запросов (CSRF)

Cookie с токенами уходят в запрос автоматически, поэтому чужой сайт может
дёрнуть наш API «руками» пользователя. Защита построена на проверке заголовка
`Origin`: глобальная зависимость `csrf_origin_guard` (`app/core/deps.py`) стоит
на всех мутирующих роутерах (`POST`/`PUT`/`PATCH`/`DELETE`) и сверяет `Origin`
со своим хостом (заголовок `Host` запроса) и списком `BASE_URL` +
`EXTRA_ALLOWED_ORIGINS`.

Почему `Origin`, а не `Referer`: браузеры всегда шлют `Origin` на
cross-origin-запросы и на same-origin `POST`, и из JS его не подделать — этого
достаточно против CSRF. `Referer` у аналитического маячка штатно указывает на
внешний сайт (переход по ссылке), поэтому проверка по нему сломала бы учёт
переходов. Запрос без `Origin` (curl, скрипты, серверные клиенты) пропускается:
CSRF — атака через браузер.

Свой origin вычисляется из `Host` запроса, а не только из `BASE_URL`: так
same-origin работает при любом домене и порту, даже если `BASE_URL` в окружении
не выставлен под текущий деплой. Если фронт отдаётся с отдельного хоста, добавьте
его в `EXTRA_ALLOWED_ORIGINS`.

## Метрики и источники

Эталоны, допуски и веса метрик собраны в `app/ml/constants.py` — каждое значение
сопровождается ссылкой на источник (Naini, Farkas, Ricketts, Powell & Humphreys,
Pallett, Little, Perrett и др.). Веса можно переопределять из админки
(таблица `metric_weights`), `ml/scoring.py` учитывает их при расчёте.

## Приватность и этика

* Явное согласие на обработку биометрии при регистрации.
* Эндпоинт удаления аккаунта и всех данных (GDPR-подобно).
* Фото изолированы по пользователю; публикация в батлах — только opt-in.

## Прозрачность расчёта

Отчёт объясняет сам себя, а не только показывает балл.

* В таблице метрик есть отклонение, допуск и z-оценка (`|отклонение| / допуск`).
* В карточке метрики — формула в терминах промежуточных переменных.
* Блок «Как посчитан итог» показывает вклад каждой категории (`балл × вес`),
  её долю в сумме вкладов и итоговую формулу со числителем и знаменателем.
* Таблица «Переменные расчёта» выводит геометрию: ширину и высоту лица, трети,
  межзрачковое расстояние, межгониальный размер и остальное.

Формулы (`METRIC_FORMULAS`) и названия переменных (`VARIABLE_LABELS`) лежат в
`app/ml/constants.py` рядом с `METRIC_SPECS`, поэтому отображение не может
разойтись с расчётом. Переменные и вклады пишутся в JSON `summary` при создании
отчёта — миграция БД не нужна, старые отчёты открываются с пустым блоком.

Проверка вручную на живом отчёте: сумма вкладов 0.400 + 1.628 + 1.686 + 0.418 +
0.607 + 0.149 = 4.888, делённая на сумму весов 1.00, даёт 4.89 — ровно тот
общий балл, что показан в отчёте.
