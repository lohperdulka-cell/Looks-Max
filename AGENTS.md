# AGENTS.md — заметки по репозиторию

## Что это
FaceMetric — веб-платформа оценки пропорций лица (ниша looks-max), студия VA digital studio.
Backend и ML на Python (FastAPI async + NumPy/OpenCV/MediaPipe/InsightFace).
Фронтенд — только Jinja2, HTML, CSS и vanilla JS. Никаких Node, bundler'ов,
TypeScript или React: это жёсткое требование заказчика.

## Команды
```bash
. .venv/bin/activate
ruff check app tests && ruff format app tests
mypy app
pytest                     # ~311 тестов, идёт около 170 секунд
uvicorn app.main:app --reload --port 8000
```

## Память и деплой (Render free, 512 МБ, жёсткий лимит)
Пики RSS, замерены в контейнере:
* MediaPipe — 237 МБ (основной провайдер, дефолт)
* InsightFace с обрезкой до трёх моделей — 274 МБ
* полный `buffalo_l` — 920 МБ, OOM-kill
* MediaPipe + WeasyPrint (PDF) — 321 МБ

Профиль сборки по умолчанию — `mp` (MediaPipe + PDF). Render Blueprint не умеет
передавать build args, поэтому дефолт в Dockerfile и есть прод-конфигурация.

**Обязательные системные библиотеки в образе.** Их отсутствие не видно в pytest,
потому что тесты идут на хосте, а не в контейнере:
* `libegl1`, `libgles2` — без них MediaPipe падает с
  `libEGL.so.1: cannot open shared object file` и молча уходит в демо-сетку.
  Баллы при этом остаются правдоподобными, поэтому баг коварный.
* `libpango-1.0-0`, `libpangoft2-1.0-0`, `libcairo2`, `libgdk-pixbuf-2.0-0`,
  `libharfbuzz0b` — WeasyPrint (PDF-экспорт).
* `fonts-dejavu-core` — кириллица в PDF. Без шрифта текст выходит квадратами.

**Проверяйте прод-профиль сборкой образа, а не только тестами.** Так нашлись обе
поломки выше. Скрипт проверки: собрать образ, поднять контейнер, прогнать
регистрацию → загрузку фото → отчёт → PDF, затем прочитать `/health`.

## Прозрачность расчёта
Формулы (`METRIC_FORMULAS`) и названия переменных (`VARIABLE_LABELS`) лежат в
`app/ml/constants.py` рядом с `METRIC_SPECS`. Держите их там: если формула
разойдётся с кодом, отчёт начнёт врать, а тесты этого не поймают.

Инвариант, закреплённый тестом: сумма вкладов категорий, делённая на сумму весов,
равна `overall_score` (погрешность 0.01). Вклад считается ПОСЛЕ добавления
гармонии — иначе сумма не сходится.

Переменные и вклады пишутся в JSON `summary` отчёта. Миграции БД не нужны,
старые отчёты открываются с пустым блоком «Как посчитан итог».

## Health-check
`/health` возвращает 200 всегда, но поле `status` = `degraded`, если БД
недоступна или ни один детектор не загрузился при выключенном демо. Код 200
выбран намеренно: Render перезапускает контейнер на неуспешный health, а
перезапуск проблему с библиотекой не чинит — получился бы цикл.

## Почта
Отправка через `app/core/mail.py` (`aiosmtplib`, extra `mail`, включён в оба
профиля образа). Без `SMTP_HOST` письмо не уходит, ссылка сброса пароля пишется
в лог. Ошибки SMTP не пробрасываются: сбой почты не должен ломать сброс пароля.
Тест поднимает настоящий SMTP-сервер (`aiosmtpd`, dev-зависимость) на localhost —
мокать отправку не нужно.

## Прочее
* Пол для метрик диморфизма берётся из профиля или с кнопок на странице оценки:
  MediaPipe его не отдаёт, `genderage` есть только у InsightFace.
* Пуш после каждого завершённого пункта прямо в `main`.
* Сложные места объясняем заказчику по-русски.

## Безопасность (грабли)
* Защита от CSRF — это `csrf_origin_guard` в `app/core/deps.py`, глобальная
  зависимость на мутирующие роутеры. Проверяется `Origin`, НЕ `Referer`:
  у аналитического маячка referer штатно внешний, проверка по нему ломает учёт
  переходов. Запрос без `Origin` пропускается (CSRF — только браузер).
  Cookie `fm_csrf`/`X-CSRF-Token` сами по себе ничего не защищают: их никто не
  проверяет, поэтому не полагайтесь на них. Заголовок `X-CSRF-Token` в ответе
  несёт ровно значение cookie `fm_csrf` — раньше там был HMAC, что расходилось
  с фронтом (JS эхо-шлёт cookie), и подключение проверки сломало бы все мутации.
* IP клиента берём через `app/core/client_ip.py`, а не `request.client.host`.
  На Render приложение за прокси, поэтому `request.client.host` — адрес прокси:
  лимиты по IP вырождаются в один общий счётчик на всех. XFF читается только при
  `TRUST_PROXY_HEADERS=true` (включён в render.yaml), берётся самый правый хоп.
* `User.show_in_battles` — реальный opt-out, а не только галочка в профиле:
  проверяется и в подборе соперника (`find_opponent`), и при старте батла.
* Пути к медиафайлам проверяются через `Path.is_relative_to`, а не строковым
  `startswith(str(root))`. Префикс пропускает соседний каталог с общим началом
  («/media_evil» начинается с «/media»).
* Индексы точек держим в ОДНОМ месте — `app/ml/metrics.py`. Второй набор в
  `landmarks.py` когда-то разошёлся с рабочим и содержал неверные значения;
  дубликат удалён, чтобы случайный импорт не вернул исправленный баг.

## Landmarks и метрики (грабли)
* Карта точек InsightFace 106 — источник ошибок. Уголки рта это 52/61 (НЕ 60/105,
  это точки губ). Правая внутренняя бровь — 102, не 97 (97 выше по y и зеркальна
  46). Индекс 30 — точка челюсти, не нос; кончик носа — 86.
* Пары зеркал для симметрии: истинная инволюция отражения, а не «похожие»
  индексы. Получена задачей о назначениях по зеркальным расстояниям, с
  проверкой взаимности. Любая ручная пара вроде 36↔90 вместо 36↔91 даёт ложную
  асимметрию.
* Координаты только изотропные. Точки, нормализованные раздельно по ширине и
  высоте, искажают все расстояния и углы аспектом кадра. Размер кадра живёт в
  `FaceLandmarks.image_size`; новые провайдеры обязаны его заполнять.
* Трихион (верх лица) берётся из bbox детектора. У схемы 106 нет точки лба.
  Без bbox лоб достраивается над контуром на `FOREHEAD_RATIO` (0.352, замерено
  на t1/grace/astronaut). Иначе верхняя треть нулевая.
* Ориентация: если после выпрямления по глазам подбородок выше трихиона, лицо
  перевёрнуто — добавляется 180°. На нормальных анфасах ветка не срабатывает.
* Ось симметрии считается по глазам и контуру, без кончика носа: смещённый нос
  не должен «создавать» асимметрию. Контур берётся через `_PointMap.contour_span`
  — это контур ИМЕННО схемы. Срез `rp[0:33]` задаёт контур только у
  InsightFace/legacy; у MediaPipe индексы 0..32 — внутренняя линия губ и крылья
  носа, и ось уезжала на десятки пикселей (асимметрия 0.23 при балле 0.0).
* Высота губ (MediaPipe) — по внешним точкам контура губ 0/17, а не по 13/14.
  13/14 — внутренние точки сомкнутой линии; у сомкнутого рта они совпадают по
  y, высота выходит нулевой и «пропорция губ» уходит в сотни (лог
  `ml.metric.implausible`). После правки на grace/astro: 400/7.1 -> 3.3/3.0.
* Провайдер по умолчанию — MediaPipe, поэтому проверять метрики нужно на нём,
  а не на InsightFace: обе ошибки выше ломали именно прод-путь и не ловились
  тестами, которые гоняют синтетику/демо.
* `PLAUSIBLE_RANGES` намеренно широкие. Они ловят ошибки единиц измерения
  (пиксели вместо пропорций), а не «некрасивую» геометрию: узкие рамки молча
  выбрасывали метрики из отчёта на шумных landmarks.
* Демо-сетка (`demo_landmarks._TEMPLATE`) обязана быть строго симметричной
  относительно x=0.5: тест `test_demo_grid_is_mirror_symmetric` требует, чтобы у
  каждой точки было точное зеркало. Собирается из реального лица с симметризацией
  по парам и откалиброванным вертикальным ремапом (трети).

## PvP-моггбатлы
Дуэли 1x1 (`app/services/mogbattles.py`, `/mogbattles`) — отдельная механика от
арены зрительских голосов (`battles.py`). Важные инварианты:
* Пока соперник не подтвердил готовность, его фото НЕ отдаётся клиенту: сервер
  не возвращает ни `image_url`, ни `photo_id`. Блюр на клиенте — только
  визуальный слой, подглядеть через network нельзя.
* Готовность подтверждают оба участника ПОСЛЕ подбора. Автоподтверждение при
  входе в очередь раскрывало бы фото без согласия владельца.
* Очки PvP (`users.pvp_points`) отдельны от ELO арены: там рейтинг двигают
  зрители, здесь — личный исход.
* Ничья — только при равных округлённых баллах, иначе показывались бы разные
  числа и надпись «Ничья».
* Комнаты переиспользуются только в статусе `waiting`; раскрытая комната не
  возвращается, иначе «Ещё дуэль» показала бы старый результат.

## Геймификация профиля
Опыт и уровни (`app/services/gamification.py`, `/api/profile/gamification`).
* XP не хранится счётчиком, а выводится из фактов (фото, отчёты, упражнения,
  голоса, дуэли, серия). Удаление отчёта автоматически снижает XP — не нужна
  миграция при смене правил и нет расхождения «в базе одно, на экране другое».
* Формулы уровней — чистые функции (`xp_for_level`, `level_from_xp`), поэтому
  проверяются тестами без БД.
* Карта активности считает действия по КАЛЕНДАРНОЙ дате в Python. Группировка
  по колонке-времени давала по строке на запись (у каждой своя секунда) и день
  всегда показывал 1 — это ловилось только на реальных данных.
* Прогресс ежедневного задания упирается в цель (`done <= target`), но XP
  начисляется за все действия: задание — про привычку, XP — про объём.

## Async SQLAlchemy
Связи в async-сессии не грузятся лениво. Любой код, который читает
`report.metrics` или `report.photo` после запроса, обязан запрашивать их через
`selectinload`, иначе `MissingGreenlet`. Это касается и сервисов (`ai.py`,
`reports.py`), и эндпоинтов (`exercises.py`).

Все связи ORM помечены `lazy="raise_on_sql"`: обращение к незагруженной связи
падает сразу и с понятной ошибкой, а не при первом запросе в проде. Тест
`test_relationships_forbid_lazy_sql` требует `raise_on_sql` у каждой связи,
поэтому новая связь не может появиться «молчаливой».

## Мастер ручной разметки
`app/ml/wizard.py` строит полный 106-точечный меш по 16 ключевым точкам через
RBF-деформацию (thin plate spline) канонического шаблона. Чистый NumPy: scipy в
ядро не входит (тяжёлые детекторы — extras). Ключевые точки (глаза, нос, рот,
подбородок, скулы, гонионы) определяются на шаблоне теми же индексами, что и
`metrics.py`, иначе ручной режим и автодетекция говорили бы о разных точках.
Автопозиции из детектора отдаются только для 106-точечной схемы: у MediaPipe
индексы другие. Тесты: `tests/test_stage2_wizard.py`.
